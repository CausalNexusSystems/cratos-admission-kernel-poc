Phase 12 — what this run actually is

- A single local process executing the CRATOS admission kernel against real Ed25519 signatures and real OS threads, on one machine, with no network interface used or required.
- Phase 12 spawns 100 concurrent OS threads, each assigned to one of 10 independently keyed logical partitions (labelled by illustrative sector names below) and to one of six roles (one legitimate-operator role plus five distinct disclosed-source submission techniques), selected by a PRNG seeded from local OS entropy at process start (see prng_seed above) — not from a fixed table known in advance.
- The threat model modeled is insider source-code disclosure, not private-key compromise: every simulated submitter in phase 12 is presumed to have the algorithm and every partition's public verifying key (public by design), but never any partition's private signing key. This matches a scenario where implementation detail has leaked but no credential has been stolen. The mechanism by which this is enforced is documented in the full technical report available under NDA.

Phase 13 — what this run actually is

- Phase 13 tests a DIFFERENT and STRICTLY STRONGER threat than phase 12: not source-code disclosure with no private key, but total compromise of one illustrative channel's issuer PRIVATE signing key. Every one of this phase's agents signs its own authorization honestly with that real key — every signature in this phase verifies; there is no forgery for the kernel to catch.
- What is tested instead is a per-channel structural limit fixed once by the embedder at kernel instantiation — here, one illustrative channel permitted only a bounded content-update budget, with every destructive/persistence action and every occupancy action capped at zero — that is never part of, and cannot be raised by, any signed authorization, no matter how genuinely it is signed. The full mechanism design is documented in the technical report available under NDA.
- Phase 13 also runs, and reports as a labelled contrast rather than a hidden gap, the SAME genuinely-signed malicious budget against the prior API that has no such limit: that API was never advertised as surviving issuer-key compromise, and this run shows concretely that it does not, so the improvement is measured against a real baseline rather than asserted.

Phase 15 — what this run actually is

- Phase 15 builds two fresh kernel instances, each with a small, finite budget on one lane, and admits a sequence of identical, ordinary legitimate requests into each until 90% of that lane's budget is consumed on both.
- One kernel then receives a final request framed as a legitimate, high-priority operation that overshoots the small remaining margin; the other receives a request of the identical magnitude framed as hostile. A final, well-formed, trivially small follow-up request is then sent to the first kernel to check whether the lockout is permanent.

Phase 15 — what this run does NOT demonstrate
